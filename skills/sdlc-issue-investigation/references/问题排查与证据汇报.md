# 问题排查与证据汇报

从用户实际遇到的现象出发，逐步弄清证据能支持的原因和影响范围。排查待优化问题时，按用户确定的目标核对当前表现、观察条件和基线。只读排查业务代码、配置、数据和已有业务文档，汇报后结束本阶段。

## 1. 确认这次看到的现象

- 确定目标项目、功能或接口，分开记录用户的操作、实际结果和预期结果。用用户能观察的行为描述。出现多种解释时，先让用户纠正理解。
- 记录已经知道的环境、部署版本或工作区、出现时间和出现频率。只要求对判断有用的精度。对不稳定的问题，区分已发生的例子和能稳定复现的条件。
- 先从这一条操作或请求追到前端、接口、服务和数据状态中的相关节点。对比时尽量保持输入、版本和环境一致。性能优化按已约定场景读取基线，再定位主要耗时或开销。

## 2. 对照已有文档和实际实现

1. 有对应任务时，先用任务入口 README 定位有效文档。按问题范围查需求回执、接口设计、批次改动、验收记录或对接文档，优先读取直接相关的段落。没有文档时，继续用用户证据、代码、确切版本和可读取的运行记录排查。
2. 用已确认的需求和契约理解当时的预期，用批次差异与验收记录追查相关变化，用相同环境和版本的请求、响应、日志或状态确认实际行为。核对文档状态、版本和记录时间。把过时资料标为历史线索。
3. 文档和实际行为不一致时，列出差异并分别标明依据。通过确认记录判断哪份约定仍有效。实际偏差、已批准变更和文档滞后分别报告。
4. 只读查看调用链、相关变更历史和可用运行记录。需要复现时，先判断操作是否会产生副作用，优先用已授权的只读路径或已有的隔离测试材料。需要写数据库、重复提交结果未知的请求、修改配置或操作线上服务才能继续时，说明缺少的证据，留下后续验证事项。

## 3. 问能区分原因的问题

先利用用户已提供的资料和能自行核实的内容。遇到证据缺口时，从仍需要区分的关键判断倒推线索，优先问一个最能缩小范围的问题。可以将紧密相关的线索合在一次提问中。

| 需要确认什么 | 可以向用户要什么 |
| --- | --- |
| 把看到的现象和服务端处理对上 | 一次失败的请求 ID。没有 ID 时，提供发生时间、环境和相关错误摘要 |
| 还原实际操作并理解预期 | 最短操作步骤、实际输出及原本期待的结果，或对应的已确认约定 |
| 判断是否与版本或环境有关 | 发生问题的一侧及实际版本，或同样操作在哪个环境表现正常 |
| 确认实际影响边界 | 一个受影响样例和一个相同条件下未受影响的样例 |

告诉用户要哪一条线索，以及它能核对什么。例如「能给我这次失败请求的 ID 吗？我想把页面上的结果和服务端处理记录对上。」让用户脱敏后再提供相关片段。收到线索后，回到对应调用节点核对，并告知用户新的发现或剩余缺口。

## 4. 判断原因和影响

- 为关键判断标出来源，例如文件与行号、请求 ID、日志时点、提交或验证结果。将触发条件、实际执行路径和用户看到的结果串起来。出现相关代码、旧文档描述或相近历史问题时，继续检查它是否与本次请求和版本相符。
- 证据能够解释本次现象时，写明已确认的原因及触发条件。线索还不足时，给出已核实事实、可以排除的范围及尚待验证的判断。未确认的原因保留为待核实。
- 影响范围写清谁受影响、在什么条件下会怎样。按相关性检查页面、接口调用方、数据、共用路径、版本、环境及已有文档。分别标明已证实、依据共用逻辑判断可能影响和待核实。超出已核查样本的范围要保留不确定性。

## 5. 汇报并停止

日常进度保持简短。查到会改变排查方向的证据时，及时说明查到了什么、能确定什么、还需要什么。最终先给结论，再写关键依据与影响范围。按情况采用以下结构：

- **结论**。问题定位在哪一步。原因是否已经确认。
- **证据**。列出能把原因和实际现象连起来的记录与位置。文档与现状有差异时说明具体内容。
- **影响范围**。写出已证实的影响、可能影响和待核实的部分。
- **待核对**。仍缺什么，以及哪项线索最能推进结论。证据充分时可省略。

汇报后结束排查。用户仅要求排查或关键证据不足时，等待用户决定或补充线索。用户已明确要求修复、优化或拟定方案且证据充分时，入口编排可将已汇报的结论交给方案阶段。排查中发现涉及后续修复或文档同步的部分，可作为影响列出。用户要求保存排查记录时，按项目约定把证据和状态写入该记录。代码修改、修复方案批准、分支选择和业务文档同步由后续工作处理。
