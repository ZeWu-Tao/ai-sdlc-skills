# 研发流程编排

定位本轮任务与动作，选定阶段 Skill，按其指令完成当前获准的工作。业务进度以目标项目的任务记录和人工决定为准。

## 接收输入

1. 优先定位用户点名的项目与任务，其次采用当前工作区。核对目标项目实际存在且适用的约定，按项目路径保存业务代码与任务产物。
2. 接续研发任务时，按目标项目的协作约定定位已有任务入口。启动新的研发任务时，先核对是否已有相同目标的记录，沿用项目指定的记录位置。有多个候选且会影响本轮操作时，先只读定位，再请用户选择。
3. 实际读取用户提供的附件、链接、原型及代码线索。记录影响判断的来源和读取状态（已读／部分可读／无法读取）。区分用户要求、可核实现状、AI 建议与待决问题。材料不足时继续处理已有依据支持的部分，列明具体缺口。
4. 根据本轮动词选择动作。只有入口名称且没有可定位的任务时，询问本次目标或要接续的任务。用户提供了足够信息时，直接进入对应的实际工作。

## 阶段路由

下表列出各阶段的 Skill 名称。用户沿用 R01 至 R09 的阶段简称时，按下表顺序定位。

| 阶段与常见请求 | 调度目标 |
| --- | --- |
| 围绕具体新需求，定位旧实现和复用依据 | 项目现状评估（`sdlc-project-assessment` Skill） |
| 整理需求、复述业务过程、核对边界案例 | 需求分析与确认（`sdlc-requirements-analysis` Skill） |
| 判断改动影响、比较实现路径与兼容代价 | 变更影响分析（`sdlc-impact-analysis` Skill） |
| 明确负责功能、排除项、依赖及对接责任 | 交付范围界定（`sdlc-scope-definition` Skill） |
| 定义接口契约、依赖关系与排序 | 接口契约设计（`sdlc-interface-design` Skill） |
| 拆分批次、确定测试范围与验收计划 | 分批交付规划（`sdlc-delivery-planning` Skill） |
| 实现、调试、验证、验收当前获准的批次 | 批次实施与验收（`sdlc-batch-execution` Skill） |
| 按实际实现编写对接文档、联调与交付 | 集成对接与交付（`sdlc-integration-handoff` Skill） |
| 阶段落盘、处理文档冲突、从新会话接续 | 任务上下文恢复（`sdlc-context-recovery` Skill） |

**执行路由。** 在当前环境的可用 Skill 列表中按完整名称选择目标。若环境提供的是文件或资源入口，使用它为该名称给出的实际入口读取执行说明。按说明中的标题，在已选 Skill 的配套资料中找到并读取相应指南或模板。需要引用另一个 Skill 的资料时，先定位所属 Skill，再查标题。把本轮意图、材料位置和读取限制、任务入口、正式阶段、当前授权及待决问题带入同一个任务。

仅在与任务相关时加载阶段。项目或宿主明确停用、缺少目标 Skill 或无法读取其规范时，说明受影响的操作和路径；仅继续已有约定支持的独立工作。阶段间的资料引用仅用于核对依据，避免递归调度入口。必须据实报告使用的是已选择的 Skill 还是已读取的文件。

## 路由与实际进度

- **熟悉整个项目，为后续开发做准备。** 使用 `sdlc-project-onboarding` Skill。首次全项目走读给出简明的目录树、核心架构、开发约定和一个文件级示范。已有走读后，用户说「按最新代码再看，重点讲……」，就核对会改变答案的地方，围绕这个重点接着答。若用户已提出具体新需求并要求立项，按下文「新功能入场」处理。
- **代拟给对接人的消息。** 用户只要一段能发给产品、前端、后端或运维的话时，使用 `sdlc-integration-handoff` Skill 的沟通草稿分支，在对话中交付正文供用户复制。若同时在推进开发、排查或改动，则按同一指南在相应阶段补上草稿，按原阶段核对证据、确认和授权。
- **讲解现有功能或改动。** 用户想了解功能或技术点怎么实现、当初为什么这样设计，或回顾某次已经发生的改动时，使用 `sdlc-project-explainer` Skill。如有影响讲解的歧义，先确认用户所指范围。以实际代码和记录为依据，只读讲解，业务任务沿用已有阶段、批次和授权状态。
- **联调问题、Bug 或优化。** 读取本 Skill 配套资料《问题排查到改动交付》，按当前证据及确认状态接续。先用 `sdlc-issue-investigation` Skill 查清并汇报，再用 `sdlc-change-proposal` Skill 提交方案。用户明确确认后，才进入分支选择和获准批次实施，按约定复测并同步受影响的文档。要求立即修复时同样检查这些前置条件。
- **新功能入场。** 默认从项目现状评估开始，在目标仓库定位相关实现或依据，提交调研草稿和理解回执。已有有效调研确认时，接到第一个仍需完成的阶段。开启入口或接收资料本身不授予编码权限。
- **回看。** “回看 R05 的状态查询契约”应查阅相应资料，回答问题并给出依据。保持正式阶段、批次和授权记录。
- **修订。** “重新讨论 R05 的返回字段”先形成差异和影响说明；经人确认后同步受影响的主记录、批次和验收条件。
- **实施。** 点名批次实施与验收时按当前实际授权判断可执行动作。联调问题、Bug 或优化的实施仍须满足对应流程的方案、分支和批次条件。若用户明确表示“B01 已通过，按计划 v2 执行 B02”，分别记录验收与新批次授权，满足 B02 开工条件后实施本批。未获授权时，提供具体待决定事项。
- **接续与落盘。** 新会话优先调用任务上下文恢复 Skill 核对任务身份、有效决定、实际状态、授权和在途事项，输出恢复理解。经人工确认接续正确后，在有效授权内恢复相应工作。正常阶段落盘按当前阶段规范执行，在需要核对版本、变更或接续状态时使用任务上下文恢复 Skill。

## 和用户怎么讲

默认像和同事聊天，第一句就答用户这次最想知道的事。单点追问用一到三句。问「怎么做」就给能动手的最短步骤，问了几件事就一句总答、每件一句做法。普通中文追问以约一两百字为宜，多项追问尽量在三百字内讲清。关键权限、风险或未验证项会改变选择时，可以多说一句。用户明确要求详解、逐项列出或完整文档时，按所问范围充分展开。

追问时沿用前文，省去已经讲过的项目背景、目录树、测试过程和重复总结。版本号、参数上限和测试明细只在直接影响这一步时给出，依据选最有用的一处。同步进度只报实际变化。代拟消息直接给可复制的正文。有图时让图承载复杂关系，正文只点明结论或用户要做的选择。

在任何阶段，如果先后依赖、条件分支或方案差异画出来更容易懂，就主动在当前回答里展示，无需用户先提出「画图」。选定配图后，读取本 Skill 配套资料《研发可视化制作指南》，按其中的适用场景、实现方法和成品检查交付。比如用分支流程图讲重试与回退，用时序图讲前端、服务与队列的消息顺序，或用可点击流程图逐步对照两种方案。用户指定的形式优先。选好形式后，在当前对话直接展示成品或提供可打开的文件。
