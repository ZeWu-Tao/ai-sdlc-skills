# 问题排查到改动交付

适用于已实现功能的联调异常、Bug 和优化请求。按任务证据与用户决定定位当前动作，沿用仍有效的阶段结论和授权。一个联调异常若最终需要新增业务行为，仍须明确并确认新的需求边界。

## 1. 排查并汇报

使用[问题排查](../../sdlc-issue-investigation/SKILL.md)，对照用户看到的现象、预期行为、已有任务文档、实际代码及运行证据。先汇报问题原因、支持结论的证据和影响范围。优化请求先核对目标、现状基线和限制。线索不足且会影响改法时，说明已核实的内容并向用户索取最关键的线索，停在排查。

用户只要求定位或分析时，提交排查报告后结束本轮。用户要求修复、优化或已明确要求给出改法时，交付排查结论后可继续只读拟定方案。已有有效排查结论时，核对证据和适用版本后沿用。

## 2. 提交方案并等待确认

使用[改动方案确认](../../sdlc-change-proposal/SKILL.md)。用白话说明问题原因、准备怎么改、影响范围、要同步的文档、改好后的可见结果及复测步骤和判据。提交后停止，等用户明确确认该方案及范围。用户仅确认排查结论、只确认部分方案或要求调整时，仍暂停依赖未决事项的实施，按反馈补齐或修订方案。确认前保持代码、测试、业务文档和工作分支原状。

## 3. 确认后选择分支并授权批次

1. 核对当前方案及用户确认的范围。用户明确延后实施时，记录决定并等待。Git 项目需要改代码时，读取目标项目适用的 `.rules/开发前分支选择.md`，按实际分支、命名和基线准备选项。已有选择仍适用于本次任务和目标分支时直接沿用，否则用 AskQuestion 或等效用户选择工具弹窗，等用户选定后才创建、切换或继续使用该分支。弹窗不可用时继续只读，直到按项目规则取得有效选择。
2. 使用有效的批次计划；小改动可将已确认方案约定为一个可独立验收的批次，明确目标、范围、依赖、复测和通过标准。需要拆分或补齐边界时，使用[分批交付规划](../../sdlc-delivery-planning/SKILL.md)。按项目约定记录方案版本、目标分支和当前批次授权。方案确认、分支选择及具体批次放行各自核对。同一条明确指令可同时覆盖多项决定，按其实际含义记录，并遵守分支选择方式。
3. 核实所选分支的工作区、代码和契约仍符合方案。若目标基线让原原因、改法、影响或验收标准发生实质变化，回到相应的排查或方案确认环节。分支和批次条件齐备后，使用[批次实施与验收](../../sdlc-batch-execution/SKILL.md)，仅实施当前获准批次。

## 4. 复测、同步文档并提交验收

- 在实际交付版本上按约定复测原问题、受影响的正常和边界场景。优化按可比的输入、环境和判据核对前后表现。保留实际结果及证据，区分本地、模拟、真实联调和未执行的场景。联调或环境操作依实际授权及对接方的配合推进；涉及对外契约、接入文档或真实联调时，使用[集成对接与交付](../../sdlc-integration-handoff/SKILL.md)处理对应事项。
- 用验证后的实际行为同步本批影响的有效需求、接口、对接或验收文档，以及相关任务记录。按已确认的范围更新具体章节，保留原有历史与确认依据。新增影响需先核对范围；找不到对应文档或相关验证受阻时，记录状态及后续处理条件。
- 交付实际改动、复测证据、同步的文档和仍待核实的事项，提交人工验收。范围内失败按本批修正并复测；需要改变已确认的行为或边界时，回到方案确认。人工通过且下一批另有有效授权后，才推进下一批。
