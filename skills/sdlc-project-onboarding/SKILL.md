# 熟悉整个项目

在目标项目做一次只读走读，让用户听懂项目怎么运转，也让后续开发有一份能回到源码核对的记录。实际开发沿用用户对那项任务的授权。

**先分清首轮和追问。** 首次熟悉整个仓库时按下面四步走，查证可以深入，给人的讲解先说主线。如果前面已经走读过，用户又说「拉了最新代码，再带我熟悉一下，重点讲怎么加插件」，直接沿用已有记录，核对新版本里会影响加插件的变化。

**追问默认给短答。** 单点一到三句，多项尽量在三百字内。问迁移，先用一句话串起落点和起步顺序，再给用户点到的每类工具各一句做法。就近点明会改变做法的权限或前提，讲到用户知道第一步就停。完整例子、命令和测试明细留给追问。用户明确要完整重讲、详细步骤或全部依据时，按所问范围充分展开。

1. **从全貌找到主线。** 确认仓库根目录和当前版本。Git 项目标明分支、提交和与本次走读有关的未提交变化，其他项目注明所读快照或日期。盘点顶层目录、服务或包、入口与适用的目录规则。读取本 Skill 配套资料《项目走读与开发示范》，按指南追踪核心路径、技术用途和同类实现。先补读说不通的连接点，再判断哪些部分已经熟悉。
2. **讲给接手项目的人听。** 先说谁用这个项目、做什么、从哪里开始用。首轮用带注释的精简目录树标出主要分工，再沿一个真实场景讲清入口、核心处理和结果。关键设计给出最有用的源码或文档依据。用户想深挖哪块，就沿那一块展开。
3. **用下一次开发检验理解。** 选用户举的例子，或选项目里确实存在的一类扩展。用第一人称逐步说出「我会先看哪个实现、把新内容放哪里、如何接到现有入口、最后怎样验证」。让用户能顺着文件找到每一步。关键连接还没找到时，明确哪一步待查，给出已经能确认的部分。
4. **把开发依据留在上下文里。** 全项目走读结束时，简短记录适用版本、参考实现、文件放置与命名、接入方式、验证入口及关键未决项。区分项目明文约定、同类代码惯例和本轮推断。后续问答直接使用这份记录，有变化只补受影响的结论。

关系画出来更清楚时，按本 Skill 配套资料《项目走读与开发示范》的「选图与核对」一节选图并核验成品。跨服务调用可用时序图，两种开发路线可按「交互路径图」一节制作可点开的图。图上已经说清的步骤，正文只提结论。

默认在对话中交付。用户要求落盘或供新会话复用时，优先更新项目已有的交接或架构笔记。若还没有此类记录，按用户指定位置或目标项目实际的文档组织方式保存，并告知下次从哪里读。保留维护人已有内容，标出本次查看的版本与待核实项。只读要求下，把同一段记录交给用户复制到下次会话。正式项目规范的修订另按维护人的要求处理。
