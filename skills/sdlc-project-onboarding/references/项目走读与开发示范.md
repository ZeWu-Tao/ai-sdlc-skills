# 项目走读与开发示范

以下是查项目的办法。首轮讲全貌时选最能说明项目的主线。追问时只查与本轮问题有关的入口、同类实现及版本变化。优先把做法和会影响它的限制讲给用户，完整目录、命令清单和测试明细按用户要求展开。

## 找到项目真正的入口

从根目录和关键子目录的约定、项目说明、工作区或构建清单开始。核对源文件、启动入口、装配配置和已有测试，辨认哪些组件独立运行、哪些共用一个进程、哪些文件由工具生成。任选一个主要使用场景，通过真实的调用、导入、注册、文件发现或配置引用，追到用户能看到的结果。说明各步的输入、处理和输出，以及状态在哪里保存或传给谁。多服务、多产品或多种独立入口的仓库，逐一定位核心模块的入口与职责，为不同主线各追一个代表场景。外部依赖追到当前能核实的边界。

看框架时分开回答两件事。第一，它在本项目里解决什么问题？用依赖清单或锁文件核对声明与版本，再到真实入口确认哪里调用、做了什么。第二，团队当初为什么选它？去找架构决策、设计文档或相关变更说明。有出处就讲当时的问题和取舍。缺少记录时直说「从代码能看到它负责……，当时选它的理由还没有找到」。同样处理目录拆分、模块边界和设计模式的来由。纯文档、配置或 Skill 仓库沿真实加载与调用方式讲解。

从项目的使用说明、命令声明和测试入口核对怎样启动、使用及验证，给出适用的工作目录和能观察到的结果。未执行的命令注明来源。文档与当前实现有出入时并列指出两处位置、差异及它影响的操作。

## 画目录树，讲清文件应该放哪儿

用文本代码块和 `├──`、`└──`、`│` 表示真实父子关系。首轮展示主要目录，每项用短语说明职责，只展开能帮用户找到核心入口的分支。追问文件应该放哪儿，直接指出落点和同类文件。用户要求看每个目录时，再按子树分段逐项标注，说明合并或未读取的范围。

对下一次改动有帮助的开发习惯才展开。先查有效的项目与目录约定、格式或依赖配置，再比对同一模块中典型的现有实现和测试。说清目录边界、命名、代码组织、公共能力怎么复用，以及该模块实际采用的错误处理、测试或生成流程。只有一个样本或不同服务做法不同时标明适用范围。规则与代码冲突时指出冲突位置及对下一次改动的影响。

## 用一个改动走通整条路

挑一个能代表项目日常开发、又能找到现有同类实现的例子，按真实依赖顺序演示。每一步给出要看的现有路径与符号、拟采取的动作、为什么排在这一步。拟新增文件注明「拟新增」，位置与命名指向真实的同类文件。确认新能力如何从公开入口被调用。到调用方或加载规则中检查，项目靠的是显式注册、自动发现、配置装配，还是上层直接引用。最后指出最贴近真实入口的测试、命令或手工操作，以及用户应观察到的变化。

例如，仓库已有插件时，可以从一个已工作的插件反向追到调用方，弄清它叫什么、谁找到它、如何执行、哪个测试会捕捉接入失败。讲新增同类插件时把这个顺序换成实际开发顺序，逐步报出该仓库的真实文件。项目没有插件时，选它实际支持的扩展类型。

给出熟悉程度时，点明已经核实的模块、主线与开发落点。若某个服务只有调用端、注册来自外部、或有子目录尚未检查，说明哪些结论受影响。从仓库静态读出的流程、已有测试定义和本次实测结果分别表述。

## 选图与核对

先看用户卡在哪个问题。问「这个项目怎么运转」，可以从一个真实入口画到可观察结果，箭头写清调用、传数据、读配置或触发任务。问「如果加一个智能体会怎样开发」，可以把同类实现、拟新增或拟改的文件、实际接入点和验证入口按开发顺序画出来，标题写明「开发示范」。两种问题都要讲时，可用两个视图切换。目录树和几句说明已能讲清的项目，可以直接用文字。

按项目情况选一种呈现方式。有 `sdlc-orchestrator` Skill 时，可按名称读取其配套资料《研发可视化制作指南》，查该方式的详细制作与检查要点。单独使用本 Skill 时，按以下做法即可。

- **探索项目。** 点开节点看职责、代码依据或拟改动作，用 HTML、CSS 和 JavaScript 制作可点击流程图。若项目确有可调参数且结果可计算，用 JavaScript 重算并在 Canvas 2D 上重画，验证边界值。若空间布局或层级遮挡影响理解，用 JavaScript 旋转三维节点坐标并投影到 Canvas 2D，检查换角度后标签和连线仍对应原模块。
- **解释主线。** 要说清条件分支或失败回退，用 Mermaid 的 `flowchart`，核对每条分支会走到哪里。要追踪入口、服务、队列之间的请求和回调，用 Mermaid 的 `sequenceDiagram`，核对参与方及先后顺序。
- **给人带走。** 培训中的角色场景可用 ImageGen 生成情景示意。需要准确标注模块或接口时，用 SVG 的节点、文本和箭头绘制矢量图。需要高清 PNG 时，可用 Playwright 驱动浏览器高密度截图。需要单页矢量 PDF 时，打印同一份矢量图稿并核对中文、页数和裁切。按用户需要交付对应成品。
- **演示状态变化。** 要连续展示一个真实过程时，用 Pillow 依次画出关键状态，借助 FFmpeg 调色板编码为循环 GIF。播放一轮，确认顺序、文字和最后可观察到的结果。当前环境无法交互时，用已核实的静态流程展示。确实无法渲染时，再用文字保留相同的步骤与依据。

每个关键节点都能在图上或图旁找到源码、配置或文档依据。现状图只连已核实的关系，外部未知部分标作「待核实」并停在边界。开发图对新文件标「拟新增」，对现有文件标出拟采取的动作。交付前查看实际成图，逐项核对文件名、符号、方向和标签。如果生成的图片写错了路径或画反了箭头，修正并复查，也可改为按已核实节点直接绘制。图默认随对话展示，需要保存时沿用用户指定的位置或项目的交接约定。

### 交互路径图

当读者既想一眼看清顺序，又想知道某一步实际落在哪个文件，把步骤做成可点的节点。一个常见用法是让读者切换「现有功能如何运行」和「如果新增同类功能，我会怎样开发」。也可以只做用户关心的一条路线，省去切换控件。若项目存在并行或条件分支，按实际关系画出分叉，并在箭头旁标明条件。

1. **准备每一步的内容。** 按真实顺序列出节点名、动作和依据。节点代表全局 Skill 时直接写名称，例如「判断意图」由 `sdlc-orchestrator` Skill 负责，它会选择 `sdlc-project-onboarding` Skill。引用配套资料时写所属 Skill 和资料标题。节点代表业务项目中的代码时，用本次走读实际核实的文件位置和符号。拟改位置说明改什么，拟新增文件说明参考了哪个已有实现。
2. **让节点真的可以点。** 优先使用当前宿主的交互可视化能力。支持内嵌网页时，可以把路线和步骤作为数据，用 HTML 按钮表示节点、CSS 排列箭头、JavaScript 响应选择。初始显示第一步的说明，切换路线时一起更新节点和详情，点节点时高亮该步，并在图旁显示动作和文件依据。窄屏可纵向排列，键盘也应能选择节点。
3. **交付可以操作的结果。** 在对话中展示交互视图。逐条切换路线、点开节点，核对高亮步骤、详情和实际文件是否一致。宿主只能展示静态内容时，改用流程图，并把每个节点的动作和路径直接写在图旁，用户仍能顺着它找到源码。
