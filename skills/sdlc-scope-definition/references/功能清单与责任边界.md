# 功能清单与责任边界

从一个可验收的业务结果开始。定位本次受委派的开发人员或团队，给每项结果找到负责交付的人、可检查的验收条件、受影响的模块和必要的对接方。范围结论写入具体任务的 `04-负责功能清单.md`。

## 确定本次交付主体

读取有效需求条目和正常、异常案例，核对采用的实现路径、已识别的影响、兼容限制和未验证前提，再读取用户委派或项目分工记录。用任务名称、主体、范围和采用决定的依据定位本次工作。已有同等效力的任务材料可以直接引用。

“本人负责”以委派记录中的人员或团队为准。分工尚未明确时，列出已有业务结果和候选责任边界，将人选标为待确认。能够按项目角色定位责任时可以使用角色。归属、代码访问能力、环境权限及具体实施授权分别核对。

## 建立功能清单

1. 将每条已确认需求和关键案例映射到可观察结果。明确是新增、改变、复用现有能力，还是需要外部交付。沿用项目编号；拆分、合并、移除条目时记录旧条目去向。
2. 按交付结果和责任分界确定粒度。同一人负责、能一次验收的多个技术步骤可以归在一项。跨方完成的功能需要分别写出各方可独立核对的交付物。
3. 为每项记录需求与方案依据、成功判据、必要异常处理、责任人、对接对象、影响与依赖。按需列明权限、数据、状态、兼容、测试和文档等配套内容。新增的未委派工作进入待确认清单。
4. 反向核对覆盖关系。每条需求都有交付、外部提供、排除、暂缓或待决定的去向；每个纳入功能都能定位到确认依据。记录漏项、重复项和处理安排。

在清单中分别写明本人提供什么、计划调整哪些对象、还会影响哪些对象、哪些部分由外部完成。受影响模块的清单供评估和联动使用，实施时依据具体批次、对象和环境的授权。

## 明确排除、暂缓与外部依赖

| 情形 | 记录内容 |
| --- | --- |
| 本期排除 | 排除项、决定依据、受影响的目标或案例 |
| 暂缓实施 | 所保留的义务、重新纳入的触发条件、处理方 |
| 外部承担 | 对方交付物、本方接收边界、依赖就绪时点和当前证据 |
| 职责待定 | 需要哪类决定、缺口阻塞哪些设计或验收、由谁协调 |

如果移除某项会使关键业务结果无法成立，提出具体取舍供人决定。外部承担的功能继续保留其对应需求和联调依赖。原方案中的条件性结论、前置批次、兼容约束以实际状态沿用。发现范围变化影响业务目标或既定方案时，标明所需决定和受影响条目。

对关键交接，明确谁提供、谁接收、谁协调分歧、谁验证及谁有权作最终验收。同一人可以承担多种角色。写明双方各交什么、最迟在哪项活动前需要、缺少时会阻塞哪一部分。分别使用“尚未约定”“已约定”“已交付待核验”“已核实可用”等状态，并记录依据。

例如，本方负责草稿服务，对接方负责编辑页面。可把“可按标识读回同一份草稿”列为本方自验结果，把“页面编辑后重新打开能看到更改”列为双方联调案例。只有对接方或有权代表其决定的人实际确认后，才能登记其接入承诺。

## 确认、变更与交接

形成草稿后提交可直接审阅的功能清单。请有权确认该范围的人员核对覆盖、排除项、责任分界、预计修改与影响对象、依赖和验收判据。已有且未变化的决定直接引用。局部确认只覆盖指明的条目。联络外部团队、调整共享资源或承诺排期需有相应授权。

在项目约定的任务目录保存清单，默认使用 `docs/ai-development/<任务名称>/04-负责功能清单.md`。核对实际写入结果，在任务 README 中记录有效版本、确认范围和未决项。资料级变更、计划分配、依赖实到和实际完成各自记录。变更时只对受影响条目重新核对和确认。

当人已确认负责功能及关键案例覆盖、修改与对接边界、必要依赖与验收责任后，可把相应范围交给接口设计。接口设计必须知道的归属冲突需先解决。尚未交付的外部资源可保留明确就绪条件。只确认部分职责时，仅在用户明确允许下推进这些条目，整体清单保持待确认。业务编码、迁移或发布按各自授权执行。
