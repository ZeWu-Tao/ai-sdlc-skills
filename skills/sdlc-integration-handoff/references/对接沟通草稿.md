# 对接沟通草稿

用户要找同事确认需求、补排查线索、解决联调卡点或约复测时，在对话中提供一段可直接复制的正文。开发和改动任务可把草稿放在当前结果或待办后面。只代拟消息时交付草稿即可，由用户自行复制发送。

## 确定希望对方做什么

- 先确认收件人和要解决的卡点。优先沿用用户指定的对象，从需求、接口约定或实际分工补足必要背景。姓名未知时直接按角色写。职责不清且会改变请求时，只问最能厘清分工的一项。
- 先复用已核实的事实和证据。把业务预期、观察到的现象、已做的检查和仍待核实的判断写准确。若缺失的是对方才能提供的线索，把它写成请求。若缺失会导致问错人、问错功能或误报事实，先向用户补问。
- 用同事聊天的口吻写。开头交代哪个功能、哪个场景卡住了，紧接着说清希望对方确认或提供什么。对方需要复现时，再给最短操作步骤和有用的证据，如环境、版本、时间、请求编号或脱敏后的字段。原因未查清时，陈述现象或待核实的问题。涉及拟议改动时，写成需要确认的选项或建议。

## 按接收方的职责写

| 发给谁 | 写什么、请对方做什么 |
| --- | --- |
| 产品 | 用一个用户场景引用有歧义的需求、原型或验收规则，请对方选定可观察的结果。涉及取舍时，补一句两种做法对用户有什么影响。 |
| 前端 | 写明页面操作、页面实际显示和期望显示，附已知的请求或响应字段。请对方核对触发请求的时机、实际传参、字段映射或页面状态，并指出需要回传的最小证据。 |
| 后端 | 写明接口或状态、最小复现方式、预期与实际返回。请对方确认约定、核对某次请求的处理结果，或给出能用于复测的响应样例。 |
| 运维 | 写明环境、服务、发生时间、已知版本和受影响范围。请对方核对实际部署版本、配置是否生效、路由或相关监控。需要执行变更时，先以请求讨论和确认的口吻写明所需配合。 |

以实际分工选用所需信息。多个角色有不同的待办时，分别给一段正文，各自只带对方完成动作需要的背景。

## 交付和后续

- 用「发给产品」等短标签标出收件对象，把可复制正文独立呈现。用户看的判断、填充提示和下一步放在正文外。取用日志、截图或示例时，只保留收件人有权看到且排查所需的片段，对凭据、个人信息和无关业务数据做脱敏处理。
- 汇报协作进度时，按实际情况标记待发送或待确认。收到用户转回的答复后，核对答复覆盖的场景和版本，再按当前阶段的规则更新证据或已确认事项。方案确认、批次放行和联调验收仍按各自的授权与证据办理。

## 示例

**发给产品**

> 想确认一下课程草稿的退出规则。原型写着「退出后保留内容」，如果用户刚编辑过但还没点保存，重新打开时，应该看到刚编辑的内容，还是上次保存的内容？这会影响退出提示和验收用例，我按你确认的结果处理。

**发给运维**

> 帮忙核对一下测试环境课程服务的部署版本。今天 14:20 左右，联调时两次相同的草稿查询返回了不同状态。对应的请求编号是 `req-demo-01`、`req-demo-02`。能查一下这两次请求分别到了哪个实例，以及实例当时跑的是哪个构建版本吗？拿到版本后我们再把复测条件对齐。
