# 开发前分支选择

在 Git 项目新增功能、修复 Bug 或实施涉及代码的优化时，先用 **AskQuestion 弹窗**让用户选择本次开发分支，再创建或切换到该分支并修改代码。联调问题、Bug 和优化的改动方案须先经用户确认，再进入分支选择。用户选定前，可查看需求、代码、历史和工作区状态，整理方案及建议。

## 先核对实际分支

- 定位这次要改的仓库和工作区，查看当前分支、跟踪的远端、未提交改动和已有 worktree（同一仓库的其他工作目录）。涉及多个仓库时，分别核对各自的分支及改动范围。
- **新增功能或优化**：查看本地和已知远端分支。按这次改动的位置、已有相关改动和目标基线，判断留在当前分支、使用已有分支或新开分支哪种更合适。推荐已有分支时，给出相关代码或提交等具体依据。
- **修复 Bug**：先获取并刷新目标仓库所有已配置、可访问的远端分支信息，再将它们与本地分支一起分析。常规仓库确认抓取映射只写远端跟踪引用后，可用 `git fetch --all --no-prune --no-tags`。若配置只覆盖部分分支或跳过某个远端，需核对远端实际分支列表，并补抓取未覆盖的可访问分支到远端跟踪引用。保留本地开发分支和未提交改动，排查阶段避免 `git pull`、合并或变基。无远端时分析现有本地分支。抓取失败或权限受限时，说明实际覆盖哪些分支、哪些仍待核实。
- 排查 Bug 时，通过相关代码和提交历史判断问题在哪些分支存在、哪个版本需要修复，以及哪些分支已有修复。按实际证据推荐修复分支或新分支的起点。若多条维护分支都受影响，把它们列为后续事项，由用户决定本次修哪条。

## 按项目习惯拟定新分支名

提议新分支时，先查当前项目明确的命名约定。如果项目没有写明约定，就参考同一仓库中近期的同类分支。新增功能参考功能分支，修 Bug 参考修复分支，优化参考同类改进，沿用项目实际使用的前缀、分隔符、大小写及任务编号格式。

弹窗里显示完整分支名和创建起点。确认前检查名称是否合法、是否与已知本地或远端分支重名。项目风格不明确或同类分支使用多套格式时，简短说明拟名依据，让用户选择或指定名称。

## 用弹窗让用户选择

使用当前 Agent 的 **AskQuestion、AskUserQuestion 或等效的用户选择工具**，实际触发可选弹窗。问题里写明仓库、当前分支、推荐分支及理由。围绕真实情况给出可选项，通常包括：

- 留在当前分支 `<当前分支>`。
- 使用已有分支 `<本地分支或远端/分支>`，并说明它与本次改动的关系。
- 从 `<明确的基线分支或提交>` 新建 `<建议分支名>`。

选项以已核实的分支和可用基线为依据。推荐项可排在首位，等用户提交选择后才执行。如果目标只存在于远端，在弹窗中说明将从哪个远端分支建立本地跟踪分支。如果当前工作区有未提交改动或目标分支在另一工作目录中使用，说明影响并给出保留原改动的做法，例如使用单独的工作目录。只在用户选定的范围内执行，禁止擅自暂存、覆盖、丢弃或搬运现有改动。

以下示例假定项目已经使用 `feature/` 和 `fix/` 前缀。实际提问时，按当前项目的命名方式拟定分支名。

> 当前在 `develop`。`feature/course-draft` 已经有草稿存储改造，这次功能会复用其中的提交。你想在该分支继续、留在 `develop`，还是从 `develop` 新开 `feature/course-preview`？

> 已核对相关分支，`release/2.8` 仍有这个 Bug，`develop` 已经修复。你想直接在 `release/2.8` 修，还是从它新开 `fix/draft-retry-2.8`？

默认选项、用户沉默或工具超时均不能视为已选择。工具不可用时，说明当前无法弹窗，并继续只读分析。等工具可用并收到选择，或用户明确允许采用其他确认方式且给出具体分支后，再进入代码修改。仓库没有 Git 分支时，先说明现状并向用户确认开发方式。

## 选定后再开工

记录用户选定的仓库、分支及需要的创建起点。执行对应的创建、切换或继续操作后，重新核对当前分支和工作区，再按任务授权改代码。一次有效选择可用于本次任务在同一仓库、同一分支上的后续工作。需要改到另一条分支，或进入一项新的功能、Bug 或优化任务时，重新用弹窗确认。

分支选择只决定在哪里开发。按原流程核对当前批次的实施授权。推送、合并、发布及处理原有改动各自遵循项目的授权要求。
