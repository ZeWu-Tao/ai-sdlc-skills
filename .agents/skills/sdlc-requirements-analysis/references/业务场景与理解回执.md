# 业务场景与理解回执

把需求材料整理成可由人核对的业务行为。优先回答用户是谁、什么动作触发流程、系统怎样处理、结果如何观察，以及哪些行为明确超出范围。

## 建立需求基线

1. 读取用户本次说明、需求文档、原型、示例和已确认的项目现状。记录来源、版本、实际读到的部分及限制，复用仍有效的人工决定。没有正式需求文档时，用用户明确说明形成草稿。
2. 统一关键术语，区分同名对象或不同状态。把目标、角色、输入、输出、主要流程、异常分支、本期范围与排除项整理为可引用条目。沿用项目已有编号。
3. 关联每个关键条目的来源、已确认范围、关联场景及未决问题。对用户已经明确指定有效范围的资料，可以直接引用其依据。原型上的按钮和示例默认值不能单独推导出发布、删除、重试、身份权限或对外发送的授权。
4. 记录用户已经确定的路径和限制；需要进一步判断的技术可行性、数据库影响和兼容成本，列入待分析项。不得凭此阶段的整理改变业务代码、运行配置、业务数据或执行环境操作。

## 区分现状、要求与待决事项

| 信息 | 如何记录 |
| --- | --- |
| 已核实的现状 | 引用代码、配置或运行证据，注明适用版本和范围。现有行为能否用于新需求需单独确认。 |
| 资料提出的要求 | 引用来源和章节，记录它对本次范围的适用情况。 |
| 用户已确认的决定 | 附确认对象、覆盖范围、依据和条件。业务要求与实现约束分别说明。 |
| AI 假设 | 说明尚未核实的前提、依据、错误时的影响及验证安排。 |
| AI 建议 | 给出建议理由、主要取舍和是否已被采纳。 |
| 未决问题 | 列出分歧、影响及决策人。区分会改变业务结果的问题和可留待技术分析的问题。 |

需求材料之间存在冲突时，按照用户当前明确决定处理其覆盖部分，指出仍无法判断的差异和影响。现有代码与目标需求不同，应分别记录两者。若尚未确定某个业务结果，请人作出决定或明确排除对应范围。可独立完成的资料整理继续推进。普通实现细节若已有约定且不改变结果或范围，可留给实施处理。

## 用场景检查解释是否一致

选择一条核心正常流程和至少一个与本需求相关的重要边界案例。每例写清前置条件、输入、判断、系统动作、可观察结果、禁止行为和关联需求。文档没有直接覆盖但规则应能推导的情况，优先采用容易暴露误解的反例。

例如，“重复生成”可能是重试同一次超时请求，也可能是用户主动生成第二个版本。分别推演两种动作会得到几份结果、怎样识别它们；现有材料无法作答时，将问题留给人决定。确认后把案例保留为验收依据。案例是待实现的预期，仅在实际执行测试后记录测试结果。

## 提交理解回执

正式整理时先将草稿保存到任务目录的 `02-业务需求理解.md`，必要时在任务 README 引用。遵循已有目录约定，缺省为 `docs/ai-development/<任务名称>/`。简要回执必须包含业务过程、关键范围和排除项、代表性案例、事实与假设、要人决定的问题、报告位置及下一步。单纯回看已有约定时，给出该约定及其来源。

确认对象包括目标和角色、业务范围、异常与权限边界、关键案例的预期、影响行为的取舍及剩余问题的安排。可以引用仍有效的既有确认。按具体版本或条目记录本次确认，局部确认只覆盖指定内容。AI 发送回执或保存草稿均不足以标为已确认。

发生变化时记录原决定、新内容、来源及受影响案例。未变化的决定继续有效；新材料省略旧要求时，先核对是否明确替代。更新有效报告和任务 README，保留尚未确认和需重新确认的部分。

## 交接给影响分析

以下条件同时具备后，才进入改动影响和实现路径分析。

- 目标、范围、关键流程和案例预期经过人确认，资料依据和决定范围可定位。
- 影响业务含义的问题已解决，或对应范围已经人明确排除；后续技术问题有影响说明和处理安排。
- 已确认需求、采用约束、现状差异、待核实假设与案例已写入任务记录并核对。

理解确认允许继续分析方案。编码、迁移、发布等操作需另行满足对应的范围、授权和前置条件。
