# 改动方案与复测计划

把已有排查结论变成一份用户能审核的改动方案。先给用户看原因、改法、影响和改好后的样子，再请用户确认具体范围。方案中的预期结果和复测步骤按计划表述，实际结果留待实施后核验。

## 1. 核对改动依据

- 读本次排查结论及关键证据。有关联任务时，从任务入口定位仍有效的需求、接口契约、批次记录和对接文档。对照相关版本的代码或运行记录，确认这次方案针对的实际条件。
- 用一两句把触发条件、原因、实际现象连起来，并给出最能支持判断的出处，如请求记录、复现结果、代码位置或已确认的约定。文档与实现有差异时，写清双方分别说明什么。
- 线索已经足够时直接提出方案。若原因仍未证实，保留待核实状态。说明哪个缺口会改变改法或影响范围，向用户索取最关键的证据。用户需要先讨论时，可以给有明确前提的备选思路，标为待核实。
- 待优化事项以用户目标和可比基线为依据，说明观察到的限制。关键指标或目标还没约定时，明确要请用户确认什么。

## 2. 说清改哪里、谁会受影响

给出能解决问题的最小方案，说明改动位置、行为边界和推荐理由。只有存在实质取舍时才列备选。触及公共接口、数据写入、权限或状态转换时，说明兼容和配合要求。修复应对照仍有效的业务预期，任何行为变更都写入用户要确认的范围。

分别说明两种影响：

- **原问题影响**。谁在什么条件下已经遇到问题，哪些调用方、版本或环境可能受影响，还有哪些部分待核实。
- **本次改动影响**。改动会涉及哪个入口、页面、接口、共用逻辑或数据。说清前后端需不需要配合、旧调用还能否继续、已有数据和在途任务是否受影响。与本次变更无关的路径按实际核对结果列出边界。不能确认时说明依据和待核实项。

## 3. 列出要同步的文档

核对已有任务文档与实际调用方使用的材料，指出需要随改动同步的文件或章节，以及需要更新的字段、示例、业务约定、流程或操作提示。已有契约仍准确时可继续沿用。历史决策与原有排查证据保留，新的决定注明变更缘由。

没有对应文档时，简短说明实际查找结果。是否补写按这次任务需要决定。当前只把文档同步事项交给用户确认，实际改动并验证后再更新受影响的文档。

## 4. 定义改好后的结果和复测

用用户或调用方能观察到的结果写验收目标。例如，原来会误报失败的操作，应显示什么状态、数据应保留什么。优化事项有指标时，写明相同输入、版本条件和观察方式，并用已确认的目标作判据。

- 从原问题的触发步骤出发，说明复测所需版本、环境、输入与预期结果。写出通过标准，例如实际请求返回、页面显示、数据状态或可重复的度量。
- 按影响挑选需要保留的正常路径和边界场景。涉及前后端时，写清谁用哪组请求、响应或页面结果来核对。涉及写入、超时或重试时，复测方案要写明怎样核对实际结果和副作用。
- 区分拟做的本地验证、模拟检查和真实联调。测试数据、环境、操作授权或对接方配合尚未到位时，列出条件。

## 5. 用白话提交方案，等用户确认

先说结论，再按实际情况说明以下几项。顺序和篇幅可以按情况调整。

- **原因与依据**。问题在哪，哪条证据能解释现象，还有什么待核实。
- **准备怎么改**。改哪一处、改成什么，为什么这样改。
- **影响范围**。原问题和本次改动分别影响谁，涉及哪些页面、接口、数据，是否需要对接方配合。
- **文档同步**。哪些已有文件和章节随改动更新，或者当前未找到对应文档。
- **改好后怎么验**。用户能看到的变化、如何复测、什么结果算通过。

末尾明确请用户确认本次改法、影响范围、文档同步和复测约定。局部确认只记录对应事项。如果用户调整目标、兼容边界或验收条件，先更新方案再交回确认。明确同意前只做必要的只读核对。

提交后停住。收到方案确认时，按项目约定记录用户确认的版本和范围，作为后续实施的输入。代码、测试、业务文档、配置和分支的操作留到后续实施，开工前沿用项目现有的授权与分支选择要求。
