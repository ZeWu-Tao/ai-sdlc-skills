# 讲解范围与证据使用

目标是让用户听完后能复述功能主线、理解关键行为，并知道需要时去哪里进一步看。讲解在对话中交付，调查限于读取已有代码、文档、改动记录和可用证据。

## 1. 先确认用户想弄懂哪一块

- 从本轮问题和已有对话判定对象与讲解角度。优先认用户实际看到的页面、按钮、行为或改动，再用任务记录、文件名和代码入口定位。用户只记得使用场景时，可沿着他做了什么、看到了什么查找对应功能。
- 在浅查能定位的范围内先自行查证。用户可能是在问整个流程或其中一步、设计取舍或运行行为、当前版本或某次改动。只有差异会改变讲解内容或结论时，才请用户确认。项目、分支或提交也仅在会影响回答时核对。
- 有多个合理解释时，用用户熟悉的话问最能区分它们的一句。有可靠候选就给出具体选项；仍找不到对象就请用户给页面、操作、原话或代码位置中的一条线索。等待回复后再深入查对应实现。
- 对象和角度明确时，简短复述本轮范围并直接讲。追问默认沿用已确认的对象和版本；用户改问其他模块、版本或改动时，再核对新增的范围。

例如，用户问「草稿生成怎么做的」，而项目里同时有页面到后端的任务流程和模型写草稿的逻辑，可先问：「你想了解从点按钮到页面拿到草稿的过程，还是 AI 怎么根据输入写出草稿？」

## 2. 按用户的问题取证

| 用户想知道的事 | 优先核对的资料和结论 |
| --- | --- |
| 这个功能怎么跑 | 从实际触发入口顺着调用、关键判断、状态变化和输出查看代码。对照有效需求、接口文档或验收例子，核对触发条件和用户可见的结果。配置、版本或部署状态会改变结果时，说明依据覆盖的范围。 |
| 当初为什么这样做 | 查已确认的方案和取舍、引入该设计的提交、PR 讨论或决策记录。讲清当时要解决的问题以及记录里的理由。能从实现看出效果时说明效果，历史原因缺少记录时标明推测及依据。 |
| 这次改动做了什么 | 定位对应批次、提交、PR 或工作区差异，按用户所指的基线核对改动前后的实际行为。查对应的验收或联调记录，说明验证覆盖的版本、场景和环境。 |

已有任务时，从任务入口定位直接相关的有效阶段文档和批次记录。有旧文档时核对日期、版本和确认状态。代码、有效约定及实际运行证据有差异时，指出差异会如何影响本次理解。证据有限时，按已查到的部分作答，并简要说明哪个结论仍待核实。代码阅读和已有运行证据各按其来源表述。

## 3. 首轮讲主线，追问再深入

- 开头直接回答核心问题。用一个正常场景把起点、关键处理和可观察的结果说清楚，或用一句前后对比说明这次改动。用同事间自然的词，术语第一次出现时顺手解释。
- 只展开会影响读者理解的关键细节，例如什么时候算完成、哪个状态控制页面、什么条件下走另一条路。复杂流程可以用短步骤或小图辅助。讲完给少量能查证的入口，例如关键代码位置、阶段文档或提交。
- 追问哪一步就沿哪一步讲。需要看代码时，指出对应入口、关键判断和结果如何传下去。需要解释历史原因时，带上出处及不确定性。需要复盘时，按事实说明变化和验证范围。

例如，已经确认用户关心「点按钮之后页面怎么拿到草稿」且代码能支持时，首轮可以说：「点生成后，后台先接下任务，页面用任务编号显示生成中。后台做完后，页面再用这个编号取回草稿。这里的『生成中』只表示任务已经接收，草稿还在生成。」如果用户接着问「刷新还能看到吗」，再查并讲任务编号怎么保存、页面重新打开后怎么找它。
