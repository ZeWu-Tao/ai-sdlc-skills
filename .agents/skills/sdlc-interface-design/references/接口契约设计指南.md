# 接口契约设计指南

为每个需要交互的功能回答三个问题：谁需要调用，提供方承诺什么结果，调用方凭什么判断下一步怎么做。输出应让另一位开发人员能推演正常和失败路径，也能分辨哪些约定仍需协商。

## 从一条调用路径开始

以“保存草稿后重新打开”为设计示例。教师保存自己名下的一份草稿，客户端随后用草稿标识读回正文。逐步核对：

| 业务节点 | 契约需要回答的问题 |
| --- | --- |
| 发起保存 | 草稿标识由谁生成？正文能否为空？身份和组织从哪里取得？服务端如何核对当前用户可修改该资源？ |
| 返回结果 | 何时表示已经持久化？如果只受理异步任务，返回什么任务标识，客户端怎样确认最终保存结果？ |
| 响应丢失 | 如何查询同一逻辑操作的结果？重试是否会重复写入？相同操作标识携带不同正文时如何处理？ |
| 重新打开 | 从哪里读回草稿？调用方如何区分无权访问、没有记录和依赖故障，分别采取什么动作？ |

示例中的问题需要按实际项目回答。先定位已有接口和调用点，看现有能力是否已满足确认过的业务预期。设计示例只能证明约定自洽，实际可用性应引用对应环境与交付版本的证据。

## 确定接口清单

读取本次功能清单、调用方和提供方分工、影响与兼容要求、设计范围和关键案例。核对代码或资料中已有的契约及对应版本。逐项映射功能与实际交互边界，包括适用的 HTTP、Agent 工具、内部公共调用、消息、回调、异步任务和流式交互。功能与接口允许多对多，纯内部处理或已有服务可以支撑功能。

每个必要接口有稳定标识，说明业务用途、提供方、消费者、类型和定位、前置条件、输入输出、读取或写入性质、拟新增／修改／复用／停用的内容。关联功能和异常案例，记录对旧消费者的兼容影响、过渡与配合要求。外部依赖标注实际就绪状态。未知状态保留来源缺口与影响。

## 写出能指导调用方的契约

- **字段语义。**记录每个关键输入输出的名称、位置、类型、业务含义、必填或可选、缺失／空值／默认语义及取值约束。按需要说明单位、时区、精度、枚举、排序、分页、文件引用和大小限制。区分调用方输入、服务端生成数据与可信上下文。
- **身份和资源范围。**说明实际采用的认证与资源授权机制、检查位置、调用前提和输出可见范围。服务端基于可信身份判断用户或组织可操作的资源；调用方自报标识、模型输出、提示词和前端按钮均不足以授予权限。开发分工、业务用户权限和当前环境操作授权分别核对。
- **状态与错误。**定义受理、处理中、部分结果、最终完成、失败和结果未知的可观测证据。说明传输结果和业务结果。为主要错误提供项目约定的稳定类别、触发条件、客户端处理、可重试条件和结果查询标识。按需覆盖参数、鉴权、资源、业务条件、外部依赖和超时。示例与诊断记录需脱敏。
- **写入与重试。**描述实际副作用、业务确认边界、操作标识及其作用范围、并发、重复请求与同键不同参数的处理。核验下游是否真正支持去重。响应超时或连接中断时先核查状态。无法确认执行结果且无可靠去重保证时，保留未知状态并说明等待或人工处理路径，禁止自动重放有副作用的请求。
- **异步与事件。**按需定义任务和事件标识、合法状态转换、终止条件、结果查询、重复或乱序回调、断开重连和取消语义。分别说明取消申请受理、执行实际停止及已经生效的动作。
- **示例。**至少给出适用的典型请求、成功响应和关键失败示例。核对字段和错误类型与定义一致。需要验证时，按授权注明环境、方法及真实结果。样例、静态检查、本地实现和目标环境可用性分别记录。

## 按依赖安排顺序

在依赖表中统一使用“前置对象 → 依赖它的对象”。每条边写明原因、前置产物或可观察条件、提供角色、实际状态以及受阻活动。身份约定、外部环境和测试数据也可作为前置对象。

| 类型 | 需要判断的条件 | 形成的顺序 |
| --- | --- | --- |
| 契约依赖 | 必须先确定哪个标识、字段含义、状态或责任边界？ | 约定及设计确认顺序 |
| 实现依赖 | 哪段实现确实需要已有的共享能力、结构或实现结果？ | 能开工的实现顺序 |
| 业务调用顺序 | 实际运行时必须先发生哪个业务动作？ | 接入方调用流程 |
| 验证依赖 | 哪个场景需要真实服务、环境、测试记录或对方实现？ | 测试、联调与验收顺序 |

1. 先识别硬性前置及就绪证据。保存后再读回约束实际调用顺序；查询实现如果只依赖已确定的草稿标识和读取契约，允许独立规划。证明整条链路仍需真实保存结果。
2. 对当前安排的活动，取其前置条件可满足的一组候选项。仅在这组中比较复杂度。按业务分支、状态处理、公共改动、兼容性、副作用与验证难度说明“低／中／高”等估计及不确定项。
3. 同组通常先安排简单、可检查的事项。优先验证高风险假设、解除其他工作的阻塞或满足明确业务优先级时，记录理由。输出可并行、被阻塞和可按顺序推进的部分。安排设计顺序、实现顺序和真实联调顺序时分别注明所采用的依赖。
4. 遇到互相依赖时先还原具体链路。轮询或回调可以形成正常的运行时交互。如果双方设计或实现都必须等对方先完成，提出先确定共同契约、拆分共同能力或调整边界的建议，交有权人员确认。模拟依赖标明能验证的范围、真实条件和后续验证时点。

## 确认范围与交付

实际设计时，在项目任务目录保存 `05-接口设计.md` 草稿并更新任务 README。提交给用户或指定确认人员核对功能覆盖、关键字段与业务行为、权限与失败处理、对外兼容、依赖与排序理由。外部共同契约引用对接方已有决定；缺少依据时记录待协调事项及对设计的影响。

当前范围的核心与关键异常场景均有契约支撑、阻塞关键判断的问题已解决或其范围已明确排除，且人确认对应版本时，可交付给批次规划。仅部分接口获得确认时，标明其范围和限制，只有在用户允许的范围内安排后续规划。对方服务尚未交付时可规划就绪条件，真实联调另行验证。将代码实施、调用真实写接口、迁移和发布的权限按具体授权独立核对。

修改已确认字段、状态或兼容策略时，记录影响的消费者、功能和顺序。改变业务、方案或分工时取得对应决定。最终面向实际调用方的交付文档应依据已实现版本及验证记录更新。
